# Express.js — Validation with `express-validator`

`express-validator` is a validation/sanitization library built as a thin wrapper around Express middleware. This note walks through both places your code uses it, explains the core pattern you need every time, flags two real bugs, and adds extra examples for things your code touches but doesn't fully use yet.

---

## 1. The Core Idea: Validation Chains Are Just Middleware

```javascript
import { query, validationResult, body, matchedData } from "express-validator";
```

- `query(field)`, `body(field)`, `param(field)` — each creates a **validation chain**: a middleware function (or array of them) that checks one specific piece of the request (`req.query`, `req.body`, `req.params`).
- You attach validators to that chain (`.isString()`, `.isEmpty()`, etc.) and pass the whole chain into your route, exactly like any other middleware:

```javascript
app.get("/api/test", query("filter").isString(), (req, res) => { ... });
```

The critical thing to understand — and the part your code is currently missing in **both** places it uses this library — is that **the chain only collects errors. It never blocks the request by itself.** You have to explicitly check the result and decide what to do.

### The 3-step pattern, every time

```javascript
app.post(
  "/api/thing",
  body("name").notEmpty(),         // 1. define the rule(s)
  (req, res) => {
    const result = validationResult(req); // 2. collect the results
    if (!result.isEmpty()) {               // 3. act on them
      return res.status(400).json({ errors: result.array() });
    }
    // ...only reached if validation passed
  },
);
```

Skip step 3, and the validators run, generate errors internally, and then get silently ignored — which is exactly what's happening in your code right now.

## 2. Walking Through Your `GET /api/test`

```javascript
app.get(
  "/api/test",
  query("filter").isString().withMessage("hi you make a big mistake"),
  (req, res) => {
    const result = validationResult(req);
    console.log(result);
    const {
      query: { filter, value },
    } = req;
    if (!filter && !value) return res.send(mockuser);
    if (filter && value)
      return res.send(mockuser.filter((user) => user[filter].includes(value)));
  },
);
```

- `query("filter")` — targets `req.query.filter`.
- `.isString()` — checks that the value is a string (query params basically always arrive as strings, so this mostly guards against `filter` being **missing entirely**, since a missing field is `undefined`, not a string, and would fail this check).
- `.withMessage("...")` — the custom error text attached if `.isString()` fails.
- `validationResult(req)` — gathers whatever errors were generated by the chain above into a `Result` object.

> ⚠️ **Bug: the result is logged, never enforced.** `console.log(result)` shows you the validation outcome in your terminal, but nothing checks `result.isEmpty()` or sends a `400`. So even a completely invalid request sails straight through to your existing logic untouched — the validator is decorative right now.

**Fixed version:**

```javascript
app.get(
  "/api/test",
  query("filter").isString().withMessage("filter must be a string"),
  (req, res) => {
    const result = validationResult(req);
    if (!result.isEmpty()) {
      return res.status(400).json({ errors: result.array() });
    }
    const { filter, value } = req.query;
    if (!filter && !value) return res.send(mockuser);
    if (filter && value)
      return res.send(mockuser.filter((user) => user[filter].includes(value)));
  },
);
```

## 3. Walking Through Your `POST /api/users`

```javascript
app.post(
  "/api/users",
  body("name").isEmpty().withMessage("name cannot be empty"),
  (req, res) => {
    const result = validationResult(req);
    console.log(result);
    const data = matchedData(req);
    console.log(data);
    const newuser = { id: mockuser[mockuser.length - 1].id, ...data };
    mockuser.push(newuser);
    return res.status(201).send(newuser);
  },
);
```

> ⚠️ **Bug: `.isEmpty()` does the opposite of what the message says.** `isEmpty()` passes **when the string has zero length** — it's checking "is this field blank?", not "is this field filled in?". Combined with the message `"name cannot be empty"`, the intent was clearly to _require_ a name. The validator you want is **`.notEmpty()`**:
> 
> ```javascript
> body("name").notEmpty().withMessage("name cannot be empty")
> ```
> 
> As written, `.isEmpty()` would actually flag an error on names that _do_ have content, and pass validation for a blank name — backwards from the stated goal. (And as in §2, this error is only logged anyway, never enforced, so right now it has no effect either way.)

### `matchedData(req)` — a useful but easy-to-misunderstand helper

```javascript
const data = matchedData(req);
const newuser = { id: mockuser[mockuser.length - 1].id, ...data };
```

`matchedData(req)` builds an object containing **only the fields that had a validation/sanitization chain defined for them** — not the entire `req.body`. Here, only `name` has a chain (`body("name")...`), so:

```json
// Client sends:
{ "name": "sara", "age": "25" }

// matchedData(req) returns:
{ "name": "sara" }   // "age" is silently dropped!
```

This is a common gotcha: people expect `matchedData` to behave like `req.body`, but it acts more like a **whitelist** — only fields you explicitly validated make it through. If you want `age` included in the new user, you need to give it its own chain too, even a very permissive one:

```javascript
app.post(
  "/api/users",
  body("name").notEmpty().withMessage("name cannot be empty"),
  body("age").optional().isString(),
  (req, res) => {
    const result = validationResult(req);
    if (!result.isEmpty()) return res.status(400).json({ errors: result.array() });
    const data = matchedData(req);
    // data now includes both name and age (if provided)
    ...
  },
);
```

## 4. Extra Examples — Beyond What Your Code Covers

### a) Validating route params (`param()`)

Your `finduserbyid` middleware manually does `parseInt` + `isNaN` checks. `express-validator` can express the same rule declaratively:

```javascript
import { param } from "express-validator";

app.get(
  "/api/users/:id",
  param("id").isInt().withMessage("id must be an integer"),
  (req, res) => {
    const result = validationResult(req);
    if (!result.isEmpty()) return res.status(400).json({ errors: result.array() });
    const typedid = parseInt(req.params.id);
    const finduser = mockuser.find((user) => user.id === typedid);
    if (!finduser) return res.sendStatus(404);
    res.send(finduser);
  },
);
```

### b) Common validators you'll reach for often

```javascript
body("email").isEmail();
body("age").isInt({ min: 0, max: 120 });
body("username").isLength({ min: 3, max: 20 });
body("password").isStrongPassword();
query("page").optional().isNumeric();
```

`.optional()` is important: without it, a field that's simply **not provided** will fail most validators (since `undefined` isn't a valid string/number/email/etc.). Add `.optional()` when a field is allowed to be missing.

### c) Sanitizers — transforming, not just checking

Validators check data; **sanitizers** clean it up. You can chain both together:

```javascript
body("name").trim().notEmpty().escape();
body("age").toInt();
body("email").normalizeEmail();
```

- `.trim()` — strips leading/trailing whitespace.
- `.escape()` — converts HTML characters to safe entities (helps prevent injection into HTML output).
- `.toInt()` — converts a validated numeric string into an actual `Number`.

When you later call `matchedData(req)`, you get back the **sanitized** values, not the raw input.

### d) Validating multiple fields at once

Just pass an array of chains instead of one:

```javascript
app.post(
  "/api/users",
  [
    body("name").notEmpty().withMessage("name is required"),
    body("age").isInt({ min: 0 }).withMessage("age must be a positive number"),
  ],
  (req, res) => { ... },
);
```

### e) A reusable error-checking middleware (avoid repeating step 3 everywhere)

Since "check `validationResult` and return 400 if it's not empty" repeats in every route, pull it into its own middleware, same idea as `finduserbyid` from the previous notes:

```javascript
const handleValidation = (req, res, next) => {
  const result = validationResult(req);
  if (!result.isEmpty()) {
    return res.status(400).json({ errors: result.array() });
  }
  next();
};

app.post(
  "/api/users",
  body("name").notEmpty().withMessage("name is required"),
  handleValidation,
  (req, res) => {
    const data = matchedData(req);
    // guaranteed valid here
  },
);
```

### f) Custom validators

For logic the built-in checks don't cover:

```javascript
body("id").custom((value) => {
  if (mockuser.some((u) => u.id === parseInt(value))) {
    throw new Error("id already exists");
  }
  return true;
});
```

## 5. Bonus: Fixing an Old Bug _with_ Validation

In the earlier middleware notes, `GET /api/test` had a gap: if only `filter` **or** only `value` was supplied (not both), neither `if` branch ran, and the request would hang with no response. Proper validation is actually the clean fix for this:

```javascript
app.get(
  "/api/test",
  [
    query("filter").optional().isString(),
    query("value").optional().isString(),
  ],
  handleValidation,
  (req, res) => {
    const { filter, value } = req.query;
    if ((filter && !value) || (!filter && value)) {
      return res.status(400).send("filter and value must be provided together");
    }
    if (!filter && !value) return res.send(mockuser);
    return res.send(mockuser.filter((user) => user[filter].includes(value)));
  },
);
```

## 6. Summary: The Validation Pipeline

```
Request
   │
   ▼
Validation chain(s)          e.g. body("name").notEmpty()
   │  (attach errors to req, don't block anything by themselves)
   ▼
validationResult(req)        collects everything into one object
   │
   ▼
result.isEmpty()?  ── No ──► res.status(400).json({ errors: result.array() })
   │
  Yes
   │
   ▼
matchedData(req)             grab only the validated/sanitized fields
   │
   ▼
Route logic runs safely
```

## 7. Bugs Found (Recap)

1. **`validationResult(req)` is computed and logged in both routes, but never checked.** No `400` is ever sent for invalid input — the validators currently have zero effect on request handling.
2. **`.isEmpty()` in the POST route is inverted logic.** It passes when `name` is blank and fails when `name` has content — the opposite of the stated intent ("name cannot be empty"). Should be `.notEmpty()`.
3. **`matchedData(req)` only returns fields with a validation chain defined.** In the POST route, this silently drops any field (like `age`) that wasn't given its own `body(...)` chain, even if the client sent it.
